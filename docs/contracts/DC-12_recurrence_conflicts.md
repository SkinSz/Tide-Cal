# TIDE DESIGN CONTRACT DC-12
# Recurrence-Specific Conflict Handling
Status: APPROVED by project owner (2026-08-25)
Depends on: Architecture Spec v0.3 §7, §8, §30 (#5), §31 (INVARIANT 9);
            DC-01 §3.1, §6; DC-02 (concurrency); DC-03 §2.1, §6.6;
            DC-07 (series/occurrence_overrides schema)
Unblocks: occurrence-level conflict resolution flows; conflict-resolution UI
          (deferred #12); recurrence UI editing
Resolves: deferred decision #5 from Spec §30

==================================================
1. PURPOSE AND SAFETY GOAL
==================================================

Defines how the EXISTING conflict machinery (DC-03) applies to recurrence
structures — series rules and occurrence overrides — plus the MINIMUM extra
rules recurrence requires. This contract invents NO recurrence semantics
beyond what the frozen spec already fixes:

  - Spec §8: a series is base event + recurrence rule + instance overrides;
    an override is identified by series_id + recurrence_id; series-level and
    occurrence-level changes are distinguished; series rules and overrides are
    separate conflict entities.
  - DC-03 §2.1 RULE [24]-R1: a series-rule change and an occurrence-override
    change on the same series are NEVER compared for conflict against each
    other; both survive independently even if concurrent.

Safety goal (Spec §13, INVARIANT 7): no concurrent user edit to any layer of
a recurring series may be silently discarded, silently deleted by an RRULE or
timezone change, or resurrected after a parent deletion in a non-deterministic
way.

Core stance: this contract is mostly a MAPPING document. Recurrence does not
get a new conflict engine; it gets precise identities, four new structural
rules (R1–R4), two invariants carried over from the spec (R5) and explicitly
out of scope (R6), and one deletion rule (D7).

==================================================
2. DEFINITIONS
==================================================

2.1  Series

     A series row (DC-07 `series` table): series_id (UUIDv4, also the
     entity_id for series-level changes), base_event_id (points at the base
     event row carrying wall-clock start/end + tz_id per Spec §7), and
     recurrence_rule — an RFC 5545 RRULE string (e.g. "FREQ=WEEKLY;BYDAY=MO").
     Tide defines NO custom recurrence DSL. The RRULE string is stored,
     exchanged, and conflicted verbatim; it is its own conflict entity:

         (series_id, "recurrence_rule")

     Base-event scalar fields (title, description, start_wall, end_wall,
     tz_id, ...) live on the events table and are ordinary per-field conflict
     entities under DC-03 exactly as for single events.

2.2  Occurrence Override

     One row per modified/cancelled occurrence (DC-07
     `occurrence_overrides`), keyed by the composite identity
     (series_id, recurrence_id). Per DC-01 §3.1 every override field is its
     own conflict entity:

         (series_id, "overrides.<recurrence_id>.<field>")

     with field in {cancelled, title, start_wall, end_wall, tz_id}.

2.3  recurrence_id — CANONICAL FORM

     recurrence_id identifies the ORIGINAL occurrence start (Spec §8).
     Canonical form: a UTC-INDEPENDENT WALL-CLOCK LOCAL-FORMAT STRING of the
     original occurrence's local start time IN THE SERIES' TIMEZONE, format
     "YYYYMMDDTHHMMSS" (RFC 5545 local DATE-TIME form, no offset suffix),
     e.g. "20260902T090000".

     Rules:
       - It is derived ONCE, at override creation, from the expansion that
         produced the occurrence, using the series tz_id AT THAT MOMENT.
       - It is NEVER rewritten afterward (see R2).
       - It contains no UTC offset and no zone suffix: it names a wall-clock
         position, not an instant. This keeps it stable across DST shifts and
         across later timezone changes of the series.
       - All-day recurring series: same string form, using the all-day
         wall-clock midnight convention of the base event's local date
         ("YYYYMMDDT000000").

2.4  Orphaned Override

     An override whose recurrence_id no longer corresponds to ANY occurrence
     generated by the CURRENT (recurrence_rule, base start, series tz_id)
     combination. Orphaned is a DISPLAY/state flag only; it is not a
     conflict record, has no participants, and never blocks synchronization.
     See R1.

2.5  Concurrency

     Defined solely by DC-02 §3: two changes are concurrent iff neither
     causality clock dominates the other. Nothing in this contract uses
     hlc_timestamp to decide anything.

3. CONFLICT ENTITY MAPPING RECAP (ALREADY FIXED — RESTATED)
==================================================

Per Spec [24], DC-01 §3.1, DC-03 §2.1/§6.6:

  - Series rule:            (series_id, "recurrence_rule")        — own entity
  - Each override field:    (series_id,
                             "overrides.<recurrence_id>.<field>") — own entity
  - Base event fields:      (base_event_id, "<field>")           — ordinary

RULE [24]-R1 restated: series-rule edits and override edits are NEVER
compared against each other. Concurrent rule edit + override edit produce
ZERO conflicts between them; both survive. Two concurrent edits OF the rule
itself are a normal DC-03 scalar conflict on "recurrence_rule". Two
concurrent edits of the SAME field of the SAME override are a normal DC-03
scalar conflict (see R3).

The NEW rules below add only what recurrence structure forces beyond this
independence.

--------------------------------------------------
RULE R1 — recurrence_id stability / orphaned overrides
--------------------------------------------------

If a change to the series (recurrence_rule edit, base-start edit, or series
tz_id edit) causes re-expansion such that an existing override's
recurrence_id no longer matches any generated occurrence, the override is
NOT silently deleted and NOT treated as a conflict. It becomes ORPHANED.

Orphan detection (precise):

    An override O = (series_id, rid) is ORPHANED iff, after applying the
    current authoritative (recurrence_rule, base_event.start_wall,
    series.tz_id), expanding the series yields NO occurrence whose canonical
    wall-clock id (§2.3 derivation) equals rid.

  - Detection is a pure function of current stored state — it is recomputed
    identically on every device after convergence, requiring NO knowledge of
    which edit orphaned the override. Deterministic.
  - Orphaned overrides remain fully synchronized rows (DC-07 schema needs no
    change; the flag is derivable, though devices MAY cache it locally for
    display).
  - Resolution (delete the orphan, or reinterpret it) is a USER action via
    deferred #12. Sync never auto-resolves.
  - An orphaned override's fields still participate in normal DC-03
    conflicts if concurrently edited while orphaned.

--------------------------------------------------
RULE R2 — RRULE change vs concurrent override edit; identity anchoring
--------------------------------------------------

Independence already holds per [24]-R1: both survive. The additional rule:

  If the new RRULE (or new base start) shifts the DATE on which the
  overridden occurrence falls, the override KEEPS its identity anchored to
  the ORIGINAL occurrence: recurrence_id is NEVER rewritten.

  Consequence: the override's content (e.g. moved start_wall, title) now
  attaches to a different effective date, or becomes ORPHANED under R1 if
  the original wall-clock position disappears entirely. Both outcomes are
  ACCEPTED v1 behavior — documented here, deterministic, identical on all
  devices. Rewriting recurrence_id on one device but not another would break
  composite identity and risk silent divergence; anchoring avoids that at
  the cost of a possibly surprising effective placement, which the UI must
  surface (deferred #12).

--------------------------------------------------
RULE R3 — override-vs-override same field same occurrence
--------------------------------------------------

Two devices concurrently set the same field of the same occurrence:

      Phone:  overrides.20260902T090000.title = "Dentist"
      Desktop: overrides.20260902T090000.title = "Doctor"

This is an ORDINARY DC-03 scalar conflict on the entity
(series_id, "overrides.20260902T090000.title"). Exactly one unresolved
conflict record per DC-03 §3/§4; both payloads preserved verbatim; no
winner chosen. Different fields of the same occurrence merge independently
(DC-03 TR-3); different occurrences never interact.

--------------------------------------------------
RULE R4 — series timezone change vs override edits
--------------------------------------------------

Changing the series' tz_id (on the base event row) is a SERIES-level change
to the ordinary conflict entity (base_event_id, "tz_id"):

  - Future expansion of NON-overridden occurrences uses the new tz_id
    (wall clock preserved, instants shift — Spec §7, INVARIANT 9).
  - Existing overrides KEEP their OWN tz_id column (they carry one per
    DC-07); their wall-clock meaning is unaffected by the series change.
  - A concurrent series-tz change and override edit touch DIFFERENT conflict
    entities → independent, both survive, zero conflicts ([24]-R1 again).
  - A series-tz change can orphan an override under R1 if the tz shift moves
    the original wall-clock position out of the expanded set (rare; handled
    by the same deterministic detection — no special case).

--------------------------------------------------
RULE R5 — DST correctness invariant (restated from Spec §7/INVARIANT 9)
--------------------------------------------------

  - Recurrence expansion ALWAYS computes occurrences as wall clock + IANA
    timezone, evaluated through an established timezone library (chrono-tz /
    TZif data). Fixed-offset arithmetic MUST NOT drive expansion across DST
    transitions.
  - Conflict records and change payloads NEVER store an expanded UTC instant
    as an authoritative value. utc_start_ms/utc_end_ms columns are DERIVED,
    non-authoritative (DC-07), and are never fed back into expansion or into
    conflict payloads. Payloads reference wall-clock forms only.

--------------------------------------------------
RULE R6 — NO "this and following" split in v1
--------------------------------------------------

v1 has NO "this and following" split operation (truncate series + spawn a
new series preserving future occurrences). That operation requires its own
design contract (identity handoff, reminder migration, conflict semantics
for the boundary occurrence) and is EXPLICITLY OUT OF SCOPE here. Users
approximate it by editing the RRULE (e.g. adding UNTIL) — which then behaves
exactly like any RRULE edit under R1/R2 above.

==================================================
4. CANCELLATION AND DELETION SEMANTICS
==================================================

4.1  Cancel ONE occurrence

     Setting cancelled=1 writes the ordinary change
     (series_id, "overrides.<rid>.cancelled", set {value: true}). It is a
     scalar field like any other under DC-03: concurrent cancel vs edit of a
     DIFFERENT field of that occurrence merge independently; concurrent
     cancel-vs-cancel is idempotent (identical values, DC-03 TR-5);
     un-cancel racing a cancel is a normal scalar conflict.

4.2  RULE D7 — series deletion dominates its overrides

     Deleting the SERIES (tombstone on entity_type "series", per DC-01 §6)
     deterministically removes ALL of its occurrence overrides on every
     device. This is NOT a conflict, even when a device concurrently edited
     or created an override.

     Justification (causality clocks): a tombstone is an operation on the
     PARENT ENTITY, and child overrides exist only beneath their parent.
     Every device that receives the series tombstone applies the same
     structural rule — delete the parent ⇒ delete everything beneath it —
     regardless of what override changes arrive before, with, or after it.
     There is no ordering hazard:

       - Override edit causally BEFORE the delete (dominated): superseded;
         the delete wins structurally. The pre-delete edit value remains
         recoverable from uncompacted change history until DC-06 compaction
         removes it; it is NOT restored afterward.
       - Override edit CONCURRENT with the delete: neither clock dominates,
         but unlike same-entity concurrency there is nothing to preserve —
         the child cannot outlive its deleted parent without violating
         INVARIANT 8's spirit (deleted entities cannot be reintroduced).
         Preserving a dangling child would force either resurrecting the
         parent (forbidden) or storing an orphan outside any series
         (meaningless). The tombstone therefore DOMINATES everything beneath
         it structurally, deterministically, identically on all peers.
       - Override edits AFTER the delete (causally dominated by knowledge of
         it) MUST be rejected by the application layer; sync itself simply
         applies D7.

     No resurrection: once the series tombstone is applied, no replayed or
     relayed override change may recreate an override row for it (the apply
     path checks parent liveness, mirroring DC-06's tombstone protection).
     Tombstone compaction timing remains DC-06's decision exclusively.

5. EXAMPLES
==================================================

5.1  R1 orphan via narrowed RRULE

     Series S, weekly Wednesdays 09:00 Europe/Berlin, starting 2026-09-02.
     Override exists: (S, "20260902T090000").start_wall = 10:00 (moved).
     Phone changes recurrence_rule to FREQ=WEEKLY;BYDAY=TH (Wednesdays gone;
     concurrent with the earlier move — independent per [24]-R1, both
     survive). Re-expansion generates only Thursdays; "20260902T090000"
     matches nothing → override flagged ORPHANED, row kept, still synced.
     Desktop converges to the same flagged-orphan state purely from current
     state — no conflict record, no deletion.

5.2  R2 identity anchored across a date shift

     Same series; RRULE changed so the overridden occurrence's WEEK NUMBER
     shifts (e.g. interval widened). The override stays keyed
     "20260902T090000" even though its content now effectively lands on a
     different generated date, or becomes orphaned if none matches. Its
     recurrence_id is byte-identical on every device, forever.

5.3  R3 ordinary scalar conflict inside an override

     Phone sets overrides.20260902T090000.start_wall = "2026-09-02T14:00";
     Desktop concurrently sets it to "2026-09-03T09:00". → exactly one DC-03
     conflict record on (S, "overrides.20260902T090000.start_wall"), both
     values in participants, local value unchanged pending resolution.

5.4  R4 independence

     Tablet changes series tz_id Europe/Berlin → America/New_York while
     Phone renames the same occurrence's title. Zero conflicts; both apply;
     the override keeps its own tz_id column; future plain occurrences expand
     in New York wall clock.

5.5  R5 DST crossing (Berlin fall-back, mirrors DC-07 §9.2)

     Daily series, 09:00 Europe/Berlin, spanning 2026-10-25 (03:00→02:00
     CEST→CET). chrono-tz expansion yields 09:00 wall clock EVERY day; the
     derived UTC instants step by +01:00→+02:00 offsets around the boundary.
     If two devices race on overrides.<id>.start_wall across that boundary,
     the payloads exchanged contain "…T09:00"-form wall strings only — never
     a raw epoch-ms winner.

5.6  D7 deletion with a racing override edit

     Desktop deletes series S while Phone concurrently cancels one
     occurrence. On convergence every device has: series tombstone present,
     ZERO occurrence_overrides rows for S, and NO conflict record. The
     cancellation change stays in history until compaction; it never
     recreates the row (no resurrection).

6. TESTABLE REQUIREMENTS
==================================================

TR-1  (R1 orphan detection) Create a weekly series with an override on one
      occurrence; concurrently narrow the RRULE so that occurrence
      disappears ([24]-R1 independence asserted: no conflict between the two
      changes). After convergence, EVERY device reports the override as
      orphaned, the row still exists with all fields intact, and no
      conflict record was created. Orphan determination is identical across
      devices and depends only on final stored state.

TR-2  (R2 anchored identity) Apply an RRULE edit that shifts an overridden
      occurrence's date. After sync, the override's recurrence_id is
      byte-identical to its pre-edit value on all devices; where the original
      wall-clock position still expands, the override attaches to it even at
      its new effective date; where it does not, TR-1 behavior holds.
      recurrence_id rewriting anywhere is a contract violation.

TR-3  (R3 scalar conflict inside an override) Concurrent same-field edits of
      one occurrence produce exactly one unresolved DC-03 conflict record on
      "overrides.<rid>.<field>" with both payloads preserved; concurrent
      different-field edits of the same occurrence produce zero conflicts
      and merge independently.

TR-4  (R4 tz independence) Concurrent series-tz change and occurrence-edit
      yield zero conflicts, both survive; post-convergence expansion of
      plain occurrences uses the new tz_id while the override retains its
      own tz_id column value.

TR-5  (R5 DST correctness) For the Berlin fall-back week (DC-07 §9.2
      example), chrono-tz expansion of a daily 09:00 series produces 09:00
      wall clock on all seven days with correct derived CET/CEST instants;
      all conflict/change payloads touching those occurrences contain
      wall-clock forms only, and no payload stores an expanded UTC instant
      as authoritative.

TR-6  (D7 no resurrection) Delete a series that has ≥1 override while ≥1
      device concurrently edits an override; after full mesh convergence
      (all pairs synced, including delayed/reordered delivery), every device
      has the series tombstoned, zero override rows, zero conflicts, and
      replaying the racing override change again is a no-op.

TR-7  (Property test — layered convergence) Randomized property test:
      generate N≥200 random schedules of series edits (rule, base fields,
      tz) interleaved with override edits (create/move/cancel/edit fields)
      executed across 3 devices with pairwise delayed, reordered, duplicated
      delivery. Final state on all devices must be IDENTICAL, and no
      override-layer or series-layer user edit may vanish except where
      explicitly permitted by this contract (D7 structural dominance; R1
      orphaning preserves data; R2 preserves identity). Any divergence or
      unexplained loss fails the run.

TR-8  (Idempotence) Re-delivering any change covered by this contract k≥1
      times in any order leaves state unchanged beyond clock advancement
      (extends DC-03 TR-5 to recurrence structures).

7. OUT OF SCOPE
==================================================

  - Recurrence EXPANSION algorithms and performance (caching, windowing,
    bounded expansion) — implementation detail, owned by the domain layer;
    this contract constrains only correctness (R5) and identity.
  - Conflict-RESOLUTION UI, including presentation of orphaned overrides —
    deferred decision #12.
  - "This and following" split operations — future feature requiring its own
    design contract (R6).
  - iCalendar import/export mapping (VEVENT/RRULE/RECURRENCE-ID translation)
    — interop boundary, Spec §26; note only that RFC 5545 RECURRENCE-ID maps
    naturally onto recurrence_id's canonical form.
  - When tombstone/history compaction may consume changes participating in
    the scenarios above — DC-06 exclusively.
